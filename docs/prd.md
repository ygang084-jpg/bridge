## 1. 배경 및 문제 정의

**국민은 매일 교량을 건너면서도, 그 다리가 지금까지 어떻게 관리되어 왔는지 알 수 없다.**

교량의 점검·보수 기록은 이미 공개되어 있다. 그러나 그 데이터는 '관리자 관점의 정적인 기록'으로만 존재하고, '지금 이 다리를 건너는 이용자'와 연결된 적이 없다. 그래서 국민이 아는 것은 기껏해야 준공연도 하나뿐이다.

### 이 제품이 바꾸려는 것

| 지금 | 바꾼 뒤 |
| --- | --- |
| "이 다리는 28년 됐습니다" | **"28년 동안 이렇게 관리되어 왔습니다"** |
| 준공연도라는 숫자 하나 | 준공 → 점검 → 보수 → 최근 점검으로 이어지는 **시간의 흐름** |
| 전문가만 읽는 정적 기록 | 오늘 건너는 사람이 읽을 수 있는 **이력과 현재** |

노후화는 연수로만 판단할 수 없다. **30년 된 다리라도 최근 보수를 마쳤다면 상태가 다르고, 15년 된 다리라도 오랫동안 손대지 않았다면 다르다.** 연수만 보여주면 오히려 오해를 만든다. 그래서 이 제품은 '나이'가 아니라 '관리의 흐름'을 보여준다.

### 왜 교량인가

- **두 안전의 중첩** — 구조물의 노후화와 교통 이용자의 안전이 한 지점에서 동시에 작용한다
- **이탈 경로의 제한** — 사고 시 즉시 벗어날 공간과 경로가 제한된다. 사후 대응보다 사전 인지가 중요하다
- **데이터의 존재** — 준공·점검·보수 이력이 이미 축적되어 있다. 없는 것을 만드는 게 아니라 있는 것을 잇는 문제다

## 2. 목표와 비목표

### 2.1 제품 목표

| ID | 목표 | 설명 |
| --- | --- | --- |
| **G-1** | 이 다리가 지금까지 **어떻게 관리되어 왔는지**를 시간순으로 이해하게 한다 | 제품의 중심. 준공부터 최근 점검까지를 하나의 흐름으로 |
| **G-2** | 오늘 그 다리를 이용할 때 알아야 할 **현재 조건**을 확인하게 한다 | 기상·통행 제한 등 오늘의 상태 |
| **G-3** | 전문 용어를 해석하지 않아도 위 두 가지를 읽을 수 있게 한다 | G-1·G-2에 걸치는 번역 원칙 |

### 2.2 비목표 (v0에서 하지 않는 것)

| 항목 | 이유 |
| --- | --- |
| **구조 안전성을 판정하지 않는다** | 이 제품은 교량이 안전한지 위험한지 스스로 판단하지 않는다. 공개된 기록과 관측값을 **잇고 번역할 뿐**이다 (§7) |
| **안전등급을 화면의 주인공으로 삼지 않는다** | 등급 문자 하나는 오해를 만든다. 등급은 이력 안의 한 항목으로 다룬다 (§F-02.1) |
| **시민 제보를 받지 않는다** | 접수 이후 처리 경로가 확보되지 않은 제보 기능은 '접수되었으나 아무 일도 일어나지 않는' 창구가 된다. v0·v1 모두에서 제외 |
| 실시간 통제 정보를 대체하지 않는다 | 통행 제한의 1차 출처는 관리기관과 내비게이션이다. 공개 데이터에 등록된 범위만 표시 |
| 대피 경로를 안내하지 않는다 | 오안내 시 인명 피해로 직결 |
| 개인 계정·로그인을 만들지 않는다 | v0는 로그인 없이 동작. 개인화는 v1 |

### 2.3 알려진 한계

| 한계 | 내용 |
| --- | --- |
| **이력의 공백이 '방치'로 오해될 수 있다** | 이력이 비어 있는 것은 점검을 안 했다는 뜻이 아니라, **공개 데이터에 없다는 뜻**이다. 이 구분이 화면에서 무너지면 제품이 불신을 만든다 (§F-05) |
| **불안을 해소하지는 못한다** | 정보를 전달하는 데까지가 한계다. 같은 화면을 보고 더 불안해지는 사용자가 나온다 |
| **행동 지침을 줄 수 없다** | '어디에 문의해야 하나'에 줄 수 있는 답은 관리기관 문의처 안내까지다 |
| 검증 방법 | §12 정성 지표로 측정한다. '더 불안해졌다'는 응답이 많으면 문구 수정으로 풀리는 문제인지, 개념 재검토가 필요한 신호인지 판단해야 한다 |

### 4.1 대상 교량 범위 `[확인 필요]`

> **§13 Q2(API 응답 샘플)를 받은 뒤 확정한다.** 응답을 보면 종별 분포와 이력 보유율이 드러난다. 지금 추측으로 정하면 되돌려야 한다.

| 구분 | v0 방침 | 근거 |
| --- | --- | --- |
| 도로교량 (자동차 통행) | 포함 | 페르소나가 실제로 건너는 대상 |
| 철도교량 | 제외 | 이용자가 상태를 알아도 취할 행동이 없음 |
| 보도육교·보행교 | 제외 | 2차 타겟과 함께 v1 |
| 지하차도·터널 | 제외 | 교량이 아님 |

**규모(종별)에 따른 방침** — 시설물안전법상 교량은 규모 기준으로 종별이 나뉘고, **종별에 따라 법정 점검 대상 여부가 달라 이력 데이터의 밀도도 갈린다.** 구체적 기준은 `[확인 필요 — 시설물안전법 시행령]`

| 안 | 내용 | 장단 |
| --- | --- | --- |
| A. 종별로 자르기 | 이력이 충분한 상위 종별만 대상 | 화면은 잘 채워지나 커버리지가 낮음 |
| **B. 전부 포함하고 상태로 구분** | 종별 무관하게 표시하되 이력 없는 곳은 '공개 정보 없음'으로 명시 | 커버리지는 높으나 빈 화면이 많음. **F-05를 정식 상태로 설계한 이유** |

**현재 방침은 B.** 단 §12 '정보 없음 비율'이 지나치게 높으면 A로 전환을 검토한다.

> **주의** — 페르소나가 매일 건너는 다리가 오히려 이력이 없는 소규모 교량일 수 있다. 대교는 잘 나오는데 동네 하천 위 다리는 텅 비는 상황이면, 정작 필요한 곳에서 작동하지 않는 서비스가 된다.

## 5. 화면 구성 및 사용자 흐름

**만드는 화면 5개** (지역명 검색은 목록 화면 재사용)

```
진입
 ├─ [위치 허용] ─→ 내 주변 교량 목록 ─→ 교량 상세 ─┬─→ 관리 이력 타임라인
 │                                                  └─→ 오늘의 상태
 │                                     └─(데이터 공백)─→ 정보 없음 안내
 └─ [위치 거부] ─→ 지역명 검색 ─→ (목록 화면에 합류)
```

| 화면 | 주요 요소 |
| --- | --- |
| **진입** | 서비스 한 줄 설명 / [내 주변 교량 찾기] / [지역명으로 찾기] / AI 고지 문구 |
| **교량 목록** | 교량명 + 거리 / 정보 상태 배지(이력 있음·부분·없음) / 지역명 검색 / 결과 없음 안내 |
| **교량 상세** | **최상단**: 한 문장 요약 + 'AI 요약' 배지<br>기본 정보: 교량명·소재지·준공연도·관리기관<br>**관리 요약**: 마지막 점검이 언제였는지, 마지막 보수가 언제였는지<br>[관리 이력 전체 보기] / [오늘의 상태 보기] / 고지 문구 |
| **관리 이력 타임라인** | 준공 → 점검 → 보수 → 최근을 시간순으로. 각 항목에 연월·종류·설명·출처·기준일 |
| **오늘의 상태** | 통행 제한 등록 여부 / 기상특보 발효 여부 / 관측값 + 출처 + 관측 시각 / 조회 실패 시 마지막 갱신 시각 |
| **정보 없음** | '공개된 ○○ 정보가 없습니다' + **'점검을 하지 않았다는 뜻이 아닙니다'** + 관리기관 문의처 |

### 핵심 시나리오

| # | 시나리오 | 관련 기능 |
| --- | --- | --- |
| S-1 | 매일 건너는 대교가 궁금해 접속 → 상세에서 "1998년 준공, 2016년 보수, 2026년 3월 최근 점검"을 확인 → "관리되고 있구나"라고 이해 | F-02, F-03 |
| S-2 | 타임라인에서 마지막 보수가 오래전임을 확인 → 판단은 사용자 몫으로 남되, 관리기관 문의처가 함께 보임 | F-03 |
| S-3 | 태풍 예보가 있는 날, 오늘의 상태에서 특보 발효와 통행 제한 등록 여부를 확인 | F-04 |
| S-4 | 이력이 공개되지 않은 교량 → '점검을 하지 않았다는 뜻이 아닙니다'와 함께 문의처 안내 | F-05 |
| S-5 | 위치 권한 거부 사용자가 지역명 검색으로 동일한 정보에 도달 | F-01 |

## 6. 기능 요구사항

각 '수용 기준'은 그대로 QA 체크리스트로 사용한다. **데이터 공백 상태를 정식 상태로 설계했기 때문에, 공공데이터 명세가 확정되기 전에도 F-01·F-02·F-03·F-05는 구현을 시작할 수 있다.**

### F-01. 내 주변 교량 목록

| 항목 | 내용 |
| --- | --- |
| 설명 | 현재 위치 기준 반경 내 교량을 목록으로 표시한다 |
| 수용 기준 | ① 진입 시 위치 권한을 요청하고, 허용하면 현재 위치 기준 목록을 표시한다<br>② 권한 거부·획득 실패 시 지역명 검색으로 대체 진입한다 — **빈 화면이나 오류로 끝나지 않는다**<br>③ 각 항목에 교량명, 거리, 정보 상태(F-05의 3단계)를 표시한다<br>④ 항목 선택 시 F-02로 이동한다<br>⑤ 반경 내 교량이 없으면 안내 문구와 검색 진입 버튼을 표시한다 |
| 의존 데이터 | 교량 위치 좌표, 교량명, 관리기관 `[확인 필요 — §13 Q2]` |
| 기본 반경 | 3km `[가설 — 사용성 테스트로 조정]` |

### F-02. 교량 상세 — 현재 개요

| 항목 | 내용 |
| --- | --- |
| 표시 항목 | 필수 : 교량명 / 소재지 / 준공연도 / 관리기관 / **마지막 점검 시점** / **마지막 보수 시점**<br>선택 : 교량 길이 / 시설물 종류 / 안전등급(§F-02.1의 규칙을 따를 것) |
| 수용 기준 | ① 화면 최상단에 '한 문장 요약'이 오고, 원문 데이터는 그 아래에 온다<br>② 요약 문장에 **'안전하다 / 위험하다'는 단정 표현을 쓰지 않는다.** 허용 형식은 '공개된 공식 정보 기준 ○○입니다'로 한정<br>③ **준공연도를 단독으로 강조하지 않는다.** 반드시 마지막 점검·보수 시점과 함께 표시한다 — 연수만 보여주면 '오래됨 = 위험함'이라는 오해를 만든다<br>④ 각 항목 옆에 출처 기관명과 데이터 기준일을 표기한다<br>⑤ 값이 없는 항목은 **임의 추정하지 않고** '공개 정보 없음'으로 표시한다<br>⑥ 화면 하단에 상시 고지 문구를 노출한다 (§7) |
| 의존 데이터 | 시설물 기본정보, 점검·보수 이력 `[확인 필요 — §13 Q2]` |

### F-02.1 안전등급 표시 규칙 (보조 정보)

> **v0.4 변경** — 안전등급은 더 이상 화면의 주인공이 아니다. 이력 흐름 안의 한 항목으로 다룬다. 표시할 경우 아래 규칙을 반드시 따른다.

| 항목 | 내용 |
| --- | --- |
| 위치 | 상세 화면 상단이 아니라 **관리 이력 안의 해당 시점에** 배치한다. 등급은 특정 점검 시점의 판정 결과이지 교량의 항상적 속성이 아니다 |
| 표시 형식 | 등급 문자 단독 표시 금지. 법정 정의 한 줄을 **같은 줄에** 병기한다 |
| 문구 출처 | **법령 원문 표현을 그대로 사용한다.** 자체 표현으로 풀어쓰지 않는다 — 풀어쓰는 순간 재해석이며 §7 위반 `[확인 필요 — 시설물안전법 시행령]` |
| 금지 | 툴팁·아코디언 등 **추가 조작이 필요한 방식으로 정의를 숨기지 않는다** |
| 병기 사항 | 등급과 통행 제한 상태는 **별개 정보**임을 명시한다 |

### F-03. 관리 이력 타임라인 ★ 제품의 중심

| 항목 | 내용 |
| --- | --- |
| 설명 | 준공부터 최근까지의 점검·보수·보강 기록을 **시간순 하나의 흐름**으로 보여준다 |
| 사건 종류 | 준공 / 정기점검 / 정밀점검 / 정밀안전진단 / 보수 / 보강 / 기타 `[종류 체계 확인 필요 — §13 Q2]` |
| 표시 요소 | 각 항목마다 : 연월 · 사건 종류 · 설명 · 출처 기관 · 데이터 기준일 |
| 수용 기준 | ① 시간 역순(최신이 위) 또는 정순 중 하나로 **일관되게** 표시한다<br>② **기록 사이의 간격을 시각적으로 드러낸다.** 사용자가 알아야 할 것은 사건 목록이 아니라 '얼마나 자주 관리되었는가'다<br>③ 각 항목의 출처와 기준일을 반드시 표기한다<br>④ 기록이 1건뿐이거나 없어도 화면이 정상 렌더링된다<br>⑤ **비어 있는 구간을 '점검하지 않은 기간'으로 표현하지 않는다.** '공개된 기록이 없는 구간'으로 표기한다<br>⑥ 이력 항목을 우리가 요약·평가하지 않는다. 기록을 그대로 나열한다 |
| 의존 데이터 | 점검·보수 이력 `[확인 필요 — §13 Q2]` |

> **이 기능의 성패는 데이터 밀도에 달려 있다.** 교량당 기록이 1~2건뿐이면 타임라인이 성립하지 않는다. Q2에서 **교량당 평균 이력 건수**를 반드시 확인할 것.

### F-04. 오늘의 상태

| 의존 데이터 | 통행 제한, 기상 특보·관측, 하천 수위 `[확인 필요 — §13 Q2]` |

### F-05. 정보 신뢰도 표시 (데이터 공백 처리)

공공데이터의 밀도와 갱신 주기 편차가 최대 리스크다. **'기록이 없거나 오래된 상태'를 예외가 아니라 정식 상태로 설계한다.**

| 상태 | 조건 | 표시 |
| --- | --- | --- |
| 이력 있음 | 준공 외 이력이 2건 이상 존재 | 타임라인 정상 표시 + 항목별 기준일 |
| 이력 부분 | 준공 정보는 있으나 이력이 1건 이하 | '공개된 관리 기록이 ○건입니다'를 명시. 타임라인은 있는 만큼만 |
| 이력 없음 | 준공 외 기록이 전혀 없음 | '이 교량은 공개된 관리 기록이 없습니다' + **'점검을 하지 않았다는 뜻이 아닙니다'** + 관리기관 문의처 |

| 항목 | 내용 |
| --- | --- |
| 수용 기준 | ① 세 상태 모두에서 화면이 정상 렌더링된다 (공백·오류 화면 금지)<br>② **'기록 없음'을 '관리하지 않음'으로 읽히게 표현하지 않는다** — 이 제품에서 가장 중요한 문구 규칙<br>③ **'기록 없음'을 '문제 없음'으로 읽히게도 표현하지 않는다**<br>④ 모든 화면에 데이터 출처와 조회 시각이 노출된다 |

## 7. AI 사용 원칙 및 표시 규칙

가장 큰 리스크는 **AI 요약이 '공식 판정'으로 오해되는 것**이다.

| 구분 | 허용 | 금지 |
| --- | --- | --- |
| AI 역할 | 공식 기록의 요약과 쉬운 말 번역 | 위험도 산정, 안전성 판정, 등급 재해석 |
| 이력 해석 | '2016년 보수 이후 2026년 점검이 이루어졌습니다' (사실 나열) | '관리가 부실합니다' / '관리가 잘 되고 있습니다' (평가) |
| 문장 형식 | '공개된 공식 기록 기준 ○○입니다' | '안전합니다' / '위험합니다' / '건너지 마세요' |
| 입력 | 공식 데이터 원문만 | 추론으로 채운 결측값 |

**표시 규칙**

1. AI가 생성한 문장은 공식 데이터와 시각적으로 구분한다 (별도 영역 + 배지)
2. 모든 화면에 상시 고지 : **'AI 분석은 참고용이며 공식 안전진단을 대체하지 않습니다.'**
3. 요약 문장 옆에 원문 기록으로 이동하는 경로를 항상 제공한다
4. **이력의 빈 구간에 대해 AI가 추측하지 않는다.** '기록이 없습니다'까지만 말한다

> 고지 문구의 최종 문안과 법적 검토 여부 `[확인 필요 — §13 Q3]`

## 9. 데이터 구조

> 이 DB는 사용자 데이터 저장소가 아니라 **공공데이터의 캐시·기록 계층**이다. §11의 'API 실패 시 마지막 갱신 시각 표시'와 §12의 '정보 없음 비율' 측정이 모두 저장을 전제한다.

| 테이블 | 역할 | 주요 항목 | 비고 |
| --- | --- | --- | --- |
| `bridges` | 교량 기본정보 캐시 | 교량명, 위경도, 준공연도, 연장, 종별, 시설물 종류, 관리기관, 문의처, 출처, 수집시각 | F-01·F-02의 기반 |
| **`bridge_history`** | **관리 이력 (핵심)** | 교량ID, 사건일자, 사건종류(준공/정기점검/정밀점검/정밀안전진단/보수/보강), 설명, 등급(해당 시), 출처, 데이터기준일 | **F-03의 본체.** 점검·보수를 분리하지 않고 하나의 사건 흐름으로 관리 |
| `bridge_restrictions` | 통행제한 캐시 | 제한 여부, 사유, 기간 | 제공 여부 `[확인 필요]` |
| `weather_snapshots` | 기상 관측 캐시 | 관측지점·거리, 풍속, 강수량, 기온, 하천수위, 관측시각, 수집시각 | 조회 실패 시 마지막 갱신으로 표시 |
| `weather_alerts` | 기상특보 | 지역코드, 특보 종류, 발효·해제 시각 | 교량이 아니라 지역에 발효됨 |
| `risk_thresholds` | 위험 표시 기준치 | 요인, 기준값, 단위, **출처명, 출처 URL** | **출처가 비면 화면에 표시하지 않는다** — §7 원칙의 강제 수단 |
| `bridge_summaries` | AI 한 문장 요약 | 요약문, 근거로 삼은 원본 값, 생성시각 | 매번 생성하지 않아 §11의 3초 요구를 충족 |
| `view_logs` | 익명 조회 기록 | 세션 식별자, 화면, 교량, 정보 상태, 발생시각 | §12 지표 측정용. 개인 식별 정보 없음 |

**관계**

- `bridges` 1:N (`bridge_history` · `bridge_restrictions` · `weather_snapshots` · `view_logs`)
- `bridges` 1:1 `bridge_summaries` (최신 기준)
- `weather_alerts`는 지역코드를 경유해 간접 연결되며 직접 연결선이 없다
- `risk_thresholds`는 독립 참조표

**저장하지 않는 것**

- **사용자 계정** — 로그인이 없으므로 `users` 테이블 자체가 존재하지 않는다
- **사용자 위치** — 조회에만 사용하고 저장하지 않는다
- **정보 상태(있음/부분/없음)** — 조회 시 계산하며, 지표 측정을 위해 `view_logs`에만 기록한다
- **`reports`(시민 제보)** — v0.4에서 삭제. §2.2 비목표

## 10. 기술 스택

> 스택을 결정한 제약은 하나다. **공공데이터 API 키와 AI API 키를 브라우저에 노출할 수 없으므로, '프론트엔드만 만든다'는 선택지가 존재하지 않는다.**

| 층 | 선택 | 대안 | 선택 이유 |
| --- | --- | --- | --- |
| 프론트엔드 | **Next.js (React)** | Vite + React | 대안은 백엔드 프로젝트를 따로 두어야 한다. 1인 개발에서 관리 대상이 둘이 되는 편이 더 큰 부담 |
| 백엔드 | **Next.js Route Handlers** | Supabase Edge Functions | 프론트와 한 프로젝트 안에 있어 화면과 API를 한 번에 지시·수정 가능 |
| 데이터베이스 | **Supabase (PostgreSQL)** | Vercel Postgres | 테이블을 화면에서 만들고 데이터를 눈으로 확인할 수 있다. **인증(Auth) 기능은 사용하지 않는다** |
| 배포 | **Vercel** | Netlify / Cloudflare Pages | 저장소에 올리면 자동 배포 |
| 캐시 갱신 | **Vercel Cron** | GitHub Actions | 배포처와 같은 곳에서 관리되어 단순 |
| AI 요약 | **서버에서 호출 후 DB 저장** | 클라이언트 직접 호출 | 대안은 키가 노출되어 선택지가 아니다 |
| 지도 | **v0 미사용** | Leaflet / 지도 SDK | §5에서 목록으로 대체. v1에서 도입 |

**미확인** — Supabase·Vercel 무료 플랜 조건은 변동이 잦다 `[확인 필요 — 각 서비스 공식 요금 페이지]`

## 15. 부록 — 이 문서와 구현의 차이 (2026-08-18)

> 이 절만 구현 과정에서 추가되었다. §1~§14 본문은 v0.4 원문 그대로다.
> 아래 항목은 **구현이 문서를 앞서간 것이 아니라, 문서 작성(2026-08-10) 이후에 내려진 결정**이다.
> 각 항목의 '현재 유효한 것'을 따르고, 다음 문서 개정(v0.5)에서 본문에 반영한다.

### 15.1 요약은 AI가 만들지 않는다 → §5 · §7 · §9 영향

| 구분 | 내용 |
| --- | --- |
| 문서 | §5 '한 문장 요약 + **AI 요약** 배지', §7 전체가 AI 사용 원칙, 상시 고지 '**AI 분석은** 참고용이며…' |
| 현재 | 요약은 **규칙 기반 문장 템플릿**으로 생성한다. AI API를 쓰지 않는다. 배지는 '**자동 요약**' |
| 왜 | 이 요약이 하는 일은 값을 정해진 틀에 끼우는 것뿐이다. AI라고 적으면 실제보다 큰 판단이 들어간 것처럼 읽혀 §7이 막으려던 오해(요약이 공식 판정으로 읽히는 것)를 오히려 키운다 |
| 상시 고지 | '이 화면의 정보는 공공데이터를 옮긴 것이며, 공식 안전진단을 대체하지 않습니다.' — 어디에도 AI가 없으므로 'AI 분석'이라 적으면 사실과 다르다 |
| §7의 지위 | 원칙 자체(판정 금지·추정 금지·원문 경로 제공·빈 구간 추측 금지)는 **모두 유효하며 코드로 강제된다.** 'AI'라는 주체만 '자동 생성'으로 바뀐다 |

### 15.2 요약 문장 형식 → §F-02 ②

| 구분 | 내용 |
| --- | --- |
| 문서 | 허용 형식을 '**공개된 공식 정보 기준 ○○입니다**'로 한정 |
| 현재 | 문장은 `1917년에 지어졌고, 최근 점검은 2025년 11월, 마지막 보수는 2023년 6월입니다.` 형태. '공개된 공식 정보 기준'이라는 정형구는 **문장 안이 아니라 요약 카드의 라벨**에 둔다 |
| 왜 | 60자 제한 안에서 정형구가 앞머리를 다 먹는다. 또 모든 교량에서 같은 8글자가 반복되면 읽히지 않고 넘겨진다. 한정 조건은 카드 라벨로 한 번 밝히는 편이 실제로 전달된다 |

### 15.3 준공 경과 연수를 강조하지 않는다 → §1 · §F-02 ③

| 구분 | 내용 |
| --- | --- |
| 이전 구현 | `1917년에 지어져 **109년이 지났고**, 가장 최근 점검은 …` |
| 현재 | 경과 연수 강조를 뺐다. 준공연도는 **최근 점검·마지막 보수와 항상 함께** 나온다 |
| 왜 | §1이 명시한 논지 그대로다 — "연수만 보여주면 오히려 오해를 만든다". 문장에서 가장 큰 숫자가 '109년'이면 §F-02 ③이 막으려던 '오래됨 = 위험함'을 문장이 스스로 만든다 |

### 15.4 안전등급 정의를 툴팁으로 숨기지 않는다 → §F-02.1

| 구분 | 내용 |
| --- | --- |
| 문서 | 툴팁·아코디언 등 추가 조작이 필요한 방식 **금지** |
| 이전 프로토타입 | 상세 화면 '안전등급' 항목에 `title` 속성 툴팁 |
| 현재 | 툴팁 제거. 등급은 **관리 이력 타임라인의 해당 시점**에, 법정 정의를 **같은 줄에 펼쳐서** 표시 |
| 단, 지금은 표시하지 않음 | 법령 원문을 대조하지 못했다(§13 **Q4** 미해소). `safetyGrades.js`의 `SAFETY_GRADE_SOURCE.url`·`verifiedOn`이 비어 있는 동안은 정의를 렌더링하지 않는다 — §F-02.1 '법령 원문 표현을 그대로'를 지킬 수 없는 상태에서 자체 표현을 내보내면 §7 위반이 된다 |
| Q4 해소 방법 | 국가법령정보센터에서 「시설물의 안전 및 유지관리에 관한 특별법 시행령」 별표를 확인해 `safetyGrades.js`의 두 값을 채우면 자동으로 표시가 켜진다 |

### 15.5 F-04는 화면만 있고 판정 로직이 없다 → §13

§13의 착수 판정("F-04는 Q2·Q3 해소 후")을 그대로 지켰다. `/bridges/[id]/today` 라우트는 존재하지만 **기준치 비교 코드가 0줄**이며, 화면은 Q2·Q3가 미해소임을 명시한다. `risk_thresholds`는 테이블만 만들고 행을 넣지 않았다 — 출처 없는 기준치가 들어가는 것을 막기 위해 `source_url`을 `not null`로 걸었다.

### 15.6 스택 전환 완료 → §10

문서가 정한 Next.js로 옮겼다. 이전 저장소는 Vite + React 스캐폴드였다. 제거한 파일과 복구 방법은 `bridge-guardian/README.md`에 적었다.

### 15.7 위치 좌표는 브라우저를 떠나지 않는다 → §11 · F-01

| 구분 | 내용 |
| --- | --- |
| 문서 | '위치 정보는 조회에만 사용하고 저장하지 않는다' |
| 구현 | 좌표를 서버로 **보내지 않는다.** 서버가 교량 목록(이름·좌표 — 공개 정보)을 내려주고, 거리 계산과 정렬을 브라우저에서 한다 |
| 왜 | 좌표를 쿼리스트링이나 GET 경로에 담으면 DB에 저장하지 않아도 **서버 접근 로그에 남는다.** '저장하지 않는다'를 지키려면 애초에 보내지 않는 편이 확실하다 |
